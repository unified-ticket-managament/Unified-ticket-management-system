# Database Migrations (Deployment Context)

## Both chains, every deploy, both paths

Every deployment path (EC2 workflow, Render `start.sh`) runs the identical two commands, in the identical order:

```bash
alembic -c alembic_rbac/alembic.ini upgrade head
alembic -c alembic_ticketing/alembic.ini upgrade head
```

Order matters only against a genuinely empty database (ticketing's tables FK into `users`, owned by the RBAC chain) — against an already-migrated database, running both is a safe no-op check, not a fresh schema creation.

## What happens if a migration fails mid-deploy

- **EC2 path**: the `pip install`/alembic steps run before the frontend build and the service restart. An alembic failure here should fail the whole GitHub Actions job (standard `set -e`-style behavior expected, though the exact script content of the EC2-side steps beyond what's in `deploy.yml` itself was not independently inspected) — meaning the old, still-running systemd service keeps serving traffic on the old schema, and the deploy simply doesn't complete. **Not confirmed**: exact rollback/cleanup behavior of a partially-applied migration in this scenario.
- **Render path**: `scripts/start.sh` uses `set -e` — a migration failure here means `uvicorn` never starts, and Render's own health check (`/health`) will fail, keeping the previous deploy's instance serving traffic (standard Render zero-downtime-deploy behavior) rather than cutting over to a broken one.

## A stale-schema symptom is easy to misdiagnose as a code bug

See [06-database/migrations.md](../06-database/migrations.md)'s "stale-schema symptom" note — an entire escalation-acceptance code path once 500'd with `UndefinedColumnError` purely because the dev database was 4 migrations behind head, with zero application-code changes needed to fix it. **Always run `alembic ... current` against `heads` for both chains before assuming a reported bug needs a code fix**, especially in any environment (like a shared dev database) that isn't guaranteed to auto-deploy on every push.

## Adding a new migration

```bash
# RBAC domain
alembic -c alembic_rbac/alembic.ini revision --autogenerate -m "message"

# Ticketing domain
alembic -c alembic_ticketing/alembic.ini revision --autogenerate -m "message"
```

**Always inspect an autogenerated diff before committing it** — this codebase's own history includes at least one instance where autogenerate proposed dropping several real, deliberately-added indexes/columns simply because they weren't declared in the current SQLAlchemy models (see [06-database/indexes.md](../06-database/indexes.md)); that drift was stripped out of the migration by hand rather than applied.

## Widening a Postgres-native enum

Use `ALTER TYPE ... ADD VALUE IF NOT EXISTS`, never a full type replacement — see the repo's own `add-postgres-enum-value` skill and [06-database/migrations.md](../06-database/migrations.md) for the exact pattern and a Postgres transaction-boundary caveat worth checking before writing one by hand.
