# Database Setup

1. Create a PostgreSQL database — a free [Neon](https://neon.tech) project is what this project actually uses. You need **both** connection string forms (Neon provides both): the async/pooled one for `DATABASE_URL`, and a direct/sync one for `ALEMBIC_DATABASE_URL`.
2. **Strongly recommended**: create a Neon **branch** for your own local development rather than pointing at the same database a deployed environment uses — see [13-developer-onboarding/local-environment.md](local-environment.md) for why.
3. Run both independent Alembic chains:

```bash
cd unified-backend
alembic -c alembic_rbac/alembic.ini upgrade head
alembic -c alembic_ticketing/alembic.ini upgrade head
```

Order matters only against a genuinely empty database (ticketing tables FK into RBAC's `users`).

4. Seed data:

```bash
python scripts/rbac_seed/seed.py
```

This seeds roles, permissions, and exactly one demo user (Super Admin) — every other synthetic demo fixture was deliberately removed from the seed script during a 2026-08-10 data cleanup, so don't expect a full cast of demo Staff/Team Lead/Account Manager accounts. Check `scripts/ticketing_seed/seed_clients.py` for demo client data if you need clients to test against.

## Confirming your schema is at head

```bash
alembic -c alembic_rbac/alembic.ini current
alembic -c alembic_ticketing/alembic.ini current
```

Compare against `heads` (`alembic -c alembic_rbac/alembic.ini heads`) — **a stale schema has repeatedly produced 500 errors that look exactly like logic bugs** in this codebase's own history (see [06-database/migrations.md](../06-database/migrations.md)). Always check this before assuming a confusing error is a code problem.

## Adding a new migration

```bash
alembic -c alembic_rbac/alembic.ini revision --autogenerate -m "message"      # RBAC domain
alembic -c alembic_ticketing/alembic.ini revision --autogenerate -m "message" # Ticketing domain
```

**Always review the autogenerated diff before committing** — this codebase has real precedent for autogenerate proposing to drop indexes/columns that are deliberate, real work simply not reflected in the current SQLAlchemy models.
