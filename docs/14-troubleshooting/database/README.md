# Troubleshooting: Database

## Problem: "It looks like a CORS error" but nothing about CORS actually changed

**Symptoms**: The browser console reports "blocked by CORS policy" / `net::ERR_FAILED` for a request that used to succeed.

**Possible Causes**: An unhandled backend exception's response carries **no `Access-Control-Allow-Origin` header at all** — unlike a normal 401/403, which correctly carries CORS headers. Confirmed three separate times in this codebase's history: (1) `ticket_audit_logs` reads hitting a Python `AuditEventType` enum missing values the Postgres type already had; (2) a missing `selectinload` import causing a `NameError` in six `UserRepository` methods; (3) the mirror-image `TicketPriority` enum gap for `CRITICAL`.

**How to Diagnose**: Reproduce the exact service-layer call directly in a throwaway script, bypassing FastAPI/HTTP entirely, to get the real traceback — don't debug CORS configuration first.

**Resolution**: Fix the actual unhandled exception (commonly a Python enum missing a value the Postgres-native enum type already has, or a missing import).

**Prevention**: When widening a Postgres-native enum via migration, always add the matching Python enum member in the same change — the two must never drift, even briefly.

**Related Documentation**: [06-database/migrations.md](../../06-database/migrations.md), [08-security/auditability.md](../../08-security/auditability.md).

## Problem: An `alembic revision --autogenerate` diff proposes dropping real indexes/columns

**Symptoms**: An autogenerate diff includes `op.drop_index(...)`/`op.drop_column(...)` for things you didn't intend to remove.

**Possible Causes**: The live database has real, deliberately-added prior work (indexes, columns) that was added via means not fully reflected in the current SQLAlchemy models — a confirmed, recurring pattern in this codebase (`ix_tickets_updated_at`, `ix_tickets_pool_view`, `ix_tickets_title_trgm`, several `interactions` indexes, `interactions.snoozed_until` were all flagged this way at least once).

**Resolution**: Manually review every autogenerated diff and strip out anything not related to your actual intended change before applying it — never blindly accept autogenerate's full output.

**Related Documentation**: [06-database/indexes.md](../../06-database/indexes.md), [06-database/migrations.md](../../06-database/migrations.md).

## Problem: Bulk-deleting `users` rows fails on an unexpected foreign key

**Symptoms**: A cleanup script deleting user rows fails midway with a foreign-key violation on a table not in your checklist.

**Possible Causes**: There are **30 distinct foreign-key columns** referencing `users.user_id` across this schema — a manual checklist is very likely to miss at least one (confirmed: `message_read_receipts.user_id` was missed once). Self-referential FKs (`manager_id`/`teamlead_id`) within the same deletion batch also need nulling before the per-row deletes, not after.

**Resolution**: Query Postgres's own `information_schema.key_column_usage`/`referential_constraints` catalogs directly to enumerate every FK column referencing `users.user_id` before attempting bulk deletes, rather than relying on a manual list.

**Related Documentation**: [06-database/relationships.md](../../06-database/relationships.md), [10-operations/recovery.md](../../10-operations/recovery.md).
