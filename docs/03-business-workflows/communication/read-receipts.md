# Read receipts (Outlook-style MDN)

An agent can tick **Request read receipt** when sending a message. If a
recipient's mail system chooses to acknowledge it, UTMS records a
per-recipient **"Read receipt received"** status on that message.

> **Release note — organizational approval required.** This feature records
> *when a recipient's mail system acknowledged a message*. The repository has
> no confirmed HIPAA/BAA statement covering read-event recording
> (`docs/08-security/phi-pii-handling.md`). Obtain organizational approval
> **before** turning the Read Receipts setting on in production. It is OFF by
> default and only a Super Admin can change it.

## What it means (and does not mean)

A receipt is an optional acknowledgement generated by the **recipient's** mail
client/system. Recipients and organisations can decline, suppress or never
send one. So the UI only ever says:

- `Read receipt received · <time>` — a receipt arrived for that recipient, or
- `No receipt received` — none has arrived.

It never says "Unread" / "Not read", and a receipt is not proof that a person
read the message. The time shown is the receipt's own `Date`, not necessarily
the moment it was opened.

## Feature switch (Settings > Email & Communication > Read Receipts)

The **database setting is the single source of truth** — there is no
environment variable. It lives in table `app_settings` (key
`read_receipts_enabled`); a missing row, bad value or any read failure all mean
**OFF**, so it cannot be enabled by accident (fresh database, failed migration).

| Switch | Behaviour |
|---|---|
| OFF (default) | Checkbox hidden; a client-supplied flag is ignored; no send asks Graph for a receipt; every payload is as before the feature existed. |
| ON | Checkbox shown in Reply / Reply All / Compose; requests honoured. |

- **Who can change it:** holders of the existing `ticket:system_config`
  permission ("Configure ticket system and storage settings"). By default that is
  **Super Admin only** (Staff, Team Lead, Account Manager and Site Lead do not
  have it). No new permission was added.
- **Who can use it:** agents who may already send external email
  (`communication:reply_external` / `communication:create`) — when it is ON.
- **Where:** the existing Settings panel (Profile > Settings), card
  *Email & Communication*. Everyone sees the current state; the toggle is
  enabled only for administrators (the server re-checks every update).
- **API:** `GET /app-settings/read-receipts` → `{read_receipts_enabled, can_manage}`;
  `PUT /app-settings/read-receipts` `{enabled}` (403 without the permission).
  Every change is written to the RBAC audit log (`settings.read_receipts_updated`).
  `GET /inbox/features` mirrors the same value for the composers.

Inbound receipt detection is **always active** (it only consumes messages
whose Graph item class marks them as read receipts), so a stray receipt can
never become a ghost client email or ticket, whatever the setting says.

## Outbound

The flag travels: composer → API request → `OutboundEnvelope.read_receipt_requested`
→ persisted in `payload.envelope` (so Retry Send and Undo Send keep it) →
Graph. Draft flows persist the flag **with the draft** (the draft-send
endpoints take no per-send options). Forward, rule forwards and system
notification mail never request receipts.

Graph is asked with its own `isReadReceiptRequested` (Graph produces the real
`Disposition-Notification-To` header; hand-built `internetMessageHeaders` are
rejected by Graph):

- new message: set on `POST /messages` (draft);
- reply / reply-all: **`createReply` / `createReplyAll` → `PATCH` (flag + recipients) → `send`**.
  The direct `/reply` and `/replyAll` actions are never used for a
  receipt-requested message (202, no usable id). Ordinary replies keep their
  existing route.

The real RFC Message-ID (`internetMessageId`) is read from the create
response, before sending, and stored in `interactions.internet_message_id`
**only after the send succeeds**. It is never inferred from Sent Items,
timestamps or conversation ids (rapid replies share a second-resolution
timestamp). `Interaction.message_id` remains a locally generated placeholder
and is never a match key.

After a successful send, one `REQUESTED` row per **To and Cc** recipient is
created in `email_read_receipts` (never Bcc). Failed or canceled sends create
none; a retry stores the successful attempt's id.

## Inbound

`EmailService.receive_email` handles a receipt **first** — before the
duplicate check, bounce check and any Interaction creation:

```
receipt  ->  consumed by ReadReceiptService (never creates an
             interaction / ticket / SLA event / rule run / notification)
bounce   ->  existing bounce handling
normal   ->  existing ingestion
```

Detection: Graph item class beginning `REPORT.IPM.Note.IPN` (observed:
`REPORT.IPM.Note.IPNRN`), requested via `$expand=singleValueExtendedProperties`
on both inbound fetch sites (Graph echoes the id as `String 0x1a`). The Graph
JSON `Content-Type` is misleading for these (`application/ms-tnef`), so for a
candidate only, the full MIME is fetched (`GET /messages/{id}/$value`) and the
`message/disposition-notification` part is parsed.

Matching (exact, nothing else):

1. `Original-Message-ID` == a stored OUTBOUND `internet_message_id`
   (a case-insensitive retry is accepted only if it yields exactly one row);
2. `Final-Recipient` (minus the `RFC822;` prefix, lower-cased) must be one of
   that message's tracked To/Cc recipients.

Never `conversationId` (thread-level), subject, timestamps, `In-Reply-To` /
`References` (absent on the observed receipt) or the local placeholder id.
Anything that does not match is consumed and logged with an outcome code.

Only `Disposition: …; displayed` marks a recipient `CONFIRMED`. Any other
disposition is stored verbatim in `disposition` and leaves the row
`REQUESTED` (no "declined" state exists until one is observed live).

Failure isolation: the receipt branch runs inside a savepoint with a broad
exception guard, never raises into the poller, and logs only outcome codes
and opaque ids (no addresses, subjects or bodies). A receipt arriving before
the send's own transaction committed is re-looked-up a bounded number of
times (1 s, then 2 s) and otherwise consumed as unmatched.

## Data

| Object | Purpose |
|---|---|
| `interactions.internet_message_id` | Real Graph Message-ID of an outbound message (nullable, partial index). |
| `email_read_receipts` | One row per tracked recipient: `status` (`REQUESTED`/`CONFIRMED`), `read_at` (receipt `Date`), `disposition` (raw), `mdn_message_id`, `received_at`, `created_at`. `UNIQUE(interaction_id, recipient_email)`; partial unique index on `mdn_message_id`; FK `ON DELETE CASCADE`. |

Only recipient, disposition and timestamps are stored — never the receipt body,
quoted content or original subject.

## API

- `GET /inbox/features` → `{ "read_receipts_enabled": bool }`.
- `read_receipt_requested` (default `false`) on: ticket reply, pre-ticket
  reply, compose (form field), and the three draft-save requests.
- Responses add `read_receipts: [{recipient_email, status, read_at}]` on thread
  messages (and the open-email root) — queried only for messages whose stored
  envelope requested a receipt, so threads that did not cost nothing extra.
  Open-email also returns `draft_read_receipt_requested`.
- RBAC: no new permission. Requesting sits inside the existing
  `communication:reply_external` / `communication:create` gates; viewing follows
  the existing visibility of the message.

## Deploy / rollback

1. Apply the Alembic ticketing migrations `e5b7d9f1a3c8` then `f7a9c1e3b5d8` (both additive; no row is inserted, so the feature starts OFF).
2. Deploy backend, then frontend.
3. After organizational approval, a Super Admin turns on Settings > Email & Communication > Read Receipts (test mailbox first, then everyone).

Rollback: a Super Admin turns the setting OFF (instant, no deploy). To remove the
schema: `alembic -c alembic_ticketing/alembic.ini downgrade 9e3a5c7b2d4f`
(drops `app_settings`, `email_read_receipts` and the new column; nothing else changes).

## Known limitations / follow-ups

- Coverage is partial by nature (recipient-controlled; one Gmail account showed
  no prompt — not generalised).
- Decline / "deleted unread" receipts have not been observed; they are consumed
  and their raw disposition kept, but never marked confirmed.
- Not implemented: an audit-log event for a confirmed receipt (it would need a
  standalone Postgres-enum migration) and a notification to the sender.
- The ticket-detail `TicketComposer` reply tab (a separate composer) has no
  checkbox; only the Mail `ReplyComposer` and `ComposeView` do.
- Status appears when a thread is opened or refreshed (the mail workspace does
  not poll an open thread).
